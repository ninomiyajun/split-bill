# 技術的負債の一覧

作業の範囲外で見つけた問題を、その場で直さずに書き留めておく一覧。直すかどうかと、いつ直すかを、後で決められるように
するためである。

## 使い方

- 作業の途中で、その作業の範囲外の問題を見つけたら、その場で直さずに、下の表に 1 行足す。
- この表に載っている行は、すべて未解消である。状態の列は持たない。解消したら、解消した変更で、その行を消す。状態を
  表の列と行の有無の 2 か所に持つと、食い違うためである。
- 1 行に 1 つの問題を書く。読んだ人が、その行だけで、どこの何が問題かを分かるように書く。
- 秘匿値、個人情報、絶対パスを書かない（`AGENTS.md` の「秘匿値と個人情報」）。パスはリポジトリの根からの相対で書く。

表の列は次のとおり。

- 識別子: `TD-<数字>` の形。下の「次に使う識別子」の行の値を使い、行を足す同じ変更で、その行の数字を 1 つ進める。
  消した行の識別子は使い回さない。計画や PR に残った識別子が、別の問題を指さないようにするためである。
- 見つけた日: `YYYY-MM-DD` の形。
- 場所: 問題のあるファイルのパス。行や関数が決まるなら、それも書く。
- 内容: 何が問題で、なぜ問題か。
- 見つけた作業: 見つけた作業の計画のファイル名（ディレクトリを付けない）か、PR の番号。計画は、閉じると置き場が
  変わるためである。

| TD-1 | 2026-10-26 | `.github/workflows/harness-docs.yml` | PR の CI で、失敗すると PR が失敗になるのは、文書の検査、秘匿値の検査（harness-secrets.yml）、検査の試験のうち 3 本（check-docs・notify・drift-scan。stack-adapter の試験は流さない）だけで、lint と型の検査は PR の合否に含まれない。drift-scan.yml は、対象のパスを変える PR で lint と型も流すが、失敗を報告に残すだけで成功で終わる。harness-docs.yml の冒頭の注釈は lint と型を「既存の CI が受け持つ」と書くが、その CI は無い。そのため、手元で `npm run check` を流さなかった変更も PR の CI を通ってしまう。層を分ける検査を入れる設計で、lint と型と試験を流す CI を足すかを決める | 骨組みとハーネスの導入の PR |
