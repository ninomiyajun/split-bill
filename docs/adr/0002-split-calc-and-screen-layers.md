# 計算の層と画面の層に分け、依存の向きを dependency-cruiser で確かめる

## 背景

最初の機能「割り勘の計算」（`docs/product-specs/even-split.md`）を作るにあたり、コードの層の分け方と依存の向きを決める必要があった。
仕様の受け入れ基準の多くは、入力の 2 つの文字列で結果が決まる。これを画面なしで単体試験で確かめられる場所に置き、後の機能も同じ形に
沿って足せるようにし、逆向きの依存が入ったら機械で止めたい。

## 判断

- 層は 2 つにする。画面の層 `src/app/` と計算の層 `src/lib/`。画面の部品は 1 つだけなので別の層にせず、Next.js の非公開のフォルダー
  `src/app/_components/` に置く（経路にならない）。
- 計算の層は、判定と計算の `src/lib/split-calc.ts`（文言を持たず構造化した値を返す）と、表示の文言と書式の `src/lib/split-display.ts`
  （2 つを合わせた表示用の値を返す `evaluateSplit` を持つ）に分ける。表示の文言と書式も計算の層に置く。文言が仕様で 1 字まで決まっていて、
  単体試験で一致を確かめたいためである。
- 割り勘の画面の部品 `src/app/_components/even-split-form.tsx` は、`evaluateSplit` の戻り値を分岐を持たずにそのまま出す（この部品の
  判断。画面の層の一般の決まりは、`ARCHITECTURE.md` の「値の判定と文言の組み立てを持たず、計算の層の戻り値を出す」）。仕様の基準の
  多くを `evaluateSplit` の単体試験で確かめ、画面の上の振る舞いだけを受け入れ確認で確かめる分け方が、この前提に立つためである。
- 画面の層が計算の層から読み込んでよいのは、表示用のファイル（`src/lib/` の `*-display.ts`）だけとする。画面から使う口は `evaluateSplit` と
  型 `SplitView` だけで、読み込む名前までは検査せず、レビューで確かめる。
- 計算の層は計算の層の中だけを読み込む（Next.js・React・ほかの包み・Node.js の組み込みのモジュールを含めて禁じる）。計算の層の中は
  相対パスで読み込む。理由: `vitest.config.mts` に `@/` の別名の設定を置いていないので、計算の層の中を別名で読み込むと、型の検査と
  build は通っても試験だけが失敗するため。
- `src/` の直下に置くのは `app/` と `lib/` だけとし、ほかの場所の `src/` のファイルが何かを読み込むと失敗にする。Next.js が決めた位置の
  ファイルを置くときは、その層を ADR で決める。
- 依存の向きは dependency-cruiser だけで確かめる。設定は根の `.dependency-cruiser.cjs`、流すコマンドは `npm run check:deps`。
  検査の対象には `src` と `templates` の両方を含め、ひな形が `src/` を読み込まないことも確かめる。型だけの読み込み、JSDoc の import、
  ambient module の中の import、`process.getBuiltinModule` の呼び出しも依存として数える。

## 検討した代わりの案

- 層を分けない（計算を画面の部品の中に書く）: 計算の誤りを画面なしで確かめられず、仕様の基準を単体試験で覆えないので採らなかった。
- 画面の部品を別の層（例: `src/components/`）に分けて 3 層にする: 部品は 1 つで、非公開のフォルダーに置けば経路にならずに画面の層の中に
  置ける。層を増やす得が無いので採らなかった。
- ESLint の `no-restricted-imports` で禁じる: 読み込む名前の文字列で判定するので、同じ先を指す書き方（`../app/page` と `@/app/page`）と
  Node.js の組み込みのモジュールの名前をすべて並べる必要があり、並べ漏れを検査が拾わないので採らなかった。
- ESLint の `import/no-restricted-paths` で禁じる: 解決した先のパスで判定するが、Node.js の組み込みのモジュールはファイルのパスに
  解決されないので禁じられず、採らなかった。
- ESLint と dependency-cruiser で役割を分ける: 検査を定めるファイルが 2 つになり、`eslint.config.mjs` を文書の地図の検査の行に
  載せることになって、lint の設定のどの変更にも検査の由来の記録が要るようになるので採らなかった。
- 文書の検査の追加の口（`scripts/harness/checks.d/`）に自前の検査を書く: import の解決（`@/` の別名、型だけの import）を自前で
  書くことになり誤りやすいので採らなかった。
- 文書の決まりだけにする: 機械で止めるという目的に反するので採らなかった。

## 結果

- 計算の層に外の包みが要るとき（例: 10 進の計算の包み）は、ADR を書いて `.dependency-cruiser.cjs` の規則に許す先を足す。
- 副作用のあるコード（通信・保存など）を足すときは、それを置く層を足す ADR を書く。
- `.dependency-cruiser.cjs` は文書の地図の「検査（依存の向き）」の行に載るので、変えるときは検査の由来の記録 `docs/harness-log.md` に行が要る。
- 検査では確かめない決まりが残る: 計算の層の中を相対パスで読み込むこと（違えば試験が失敗して気づける）、画面が読み込む名前、
  計算の層の純粋さ（日時・乱数・通信・保存は読み込みなしで使える）、何も読み込まない `src/` の直下の別の場所のファイル。これらはレビューで確かめる。
